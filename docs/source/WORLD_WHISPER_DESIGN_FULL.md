『世界のささやき（World Whisper）』アプリケーション設計方針書 (V4)
1. 概要とコンセプト定義
1.1 プロジェクト名称とコンセプト
プロジェクト名： 世界のささやき（World Whisper）
サブタイトル： 〜新たな視点と内なる自分が交差する、セレンディピティの補助線〜
本アプリケーションは、「観光情報を提供する案内アプリ」ではない。ユーザーがいる場所・時間・状況に応じて、新たな観点や予期せぬ発見（セレンディピティ）をもたらし、世界を見る新しい視点をそっと提示するレンズとなる存在である。
1.2 目的と本質的価値
世界の再発見： 日常の場所や一度訪れた場所であっても、「まだ見えていなかった意味」に気づく体験を提供する。
対話の媒介（Cognitive Lens）： AIが一方的に答えを与えるのではなく、世界と内なる自分の間に入り、観察や内省を深めるための「交差点（媒介）」となる。
内なる自分との対話： 外の世界からのふとしたささやき（問いかけ）を通して、ユーザー自身の思考や感情、記憶を呼び覚ます。
1.3 基本思想と対話の構造
人が体験しているのは単なる「物理的な場所」ではない。同じ場所であっても、時間、天候、季節、移動の流れ、その人の過去の経験や関心によって意味は動的に変化する。そのため、単なる位置情報ではなく「文脈（コンテキスト）」の理解が不可欠となる。
構造定義：
世界（背景・歴史・流動） → AI（解釈・ささやき） → 内なる自分（気づき・内省）
AIは知識を誇示するガイドではなく、世界を見るためのレンズ・補助線となる。「ここは○○です」と解説するのではなく、「この場所を、こういう視点で見ると面白いかもしれません」という形で、ユーザー自身の能動的な発見を支援する。

1.5 体験イメージ・トリガー・入出力構成
体験イメージ（例：港にいる場合）：
単なる説明： 「博多港は国際港です」
本アプリのささやき： 「今見えている船の流れは、昔から続く福岡と島・大陸をつなぐ海の道の一部です」のように、現在の体験と歴史・背景を結びつける。
トリガー設計（控えめな提案型）： 余白を大切にするため完全自動通知ではなく控えめな提案型とする。
AIが周囲の状況・文脈を認識する
「ささやき（気づきの候補）」をそっと提示する（例：「この場所について、少し面白い話があります」）
ユーザーが興味を持ったものだけ深掘りし、内なる思考を巡らせる
入力情報： GPS、時刻、天候、気温、季節、移動経路、滞在時間、ユーザーの興味、音声入力、タッチ操作（※初期価値は「見る対象の認識」ではなく「意味の発見」に置く）。
出力体験（Even G2等への提示）： 大量の情報表示は不要。「今、この瞬間に一つだけ視点を増やす」ことに特化する。

3. データと文脈理解（Context Sensing）の設計
3.1 コンテキストデータの階層
短期エピソード文脈（リアルタイムセンシング）： SDK位置情報（緯度経度・位置精度）、現在時刻、天候・気温、位置の安定・文脈変化・滞在時間。徒歩・車・船などの移動形態はSDKから直接取得できる前提にせず、将来の補助文脈候補とする。
長期セマンティック文脈（ユーザーモデル）： ユーザーの興味関心テーマ（歴史、港湾文化、建築、自然等）、過去に反応を示した視点のカテゴリ。
空間・歴史的背景文脈（ナレッジベース）： 対象地点が持つ歴史的経緯、地理的特徴、関連する文化・流動の背景情報。
3.2 プロンプト生成ロジック例
System Prompt:
あなたはユーザーと世界を繋ぐ「ささやき（視点・問いかけ）」を作る媒介です。
回答や解説、長文の説明は禁止します。
与えられた文脈（場所、時間、天気、移動背景、興味）を解釈し、
ユーザーが思わず周りの景色を見渡したり、自らの思考を深めたくなるような「1つだけの新しい視点・問いかけ」を、
50文字以内の日本語で1文生成してください。

Input Context:
- 場所: 博多港周辺
- 移動文脈: バスから降りて徒歩に移動、港湾施設を注視
- 天候/時刻: 晴れ / 15:30
- ユーザー関心: 交易史、船舶、地理
4. UI/UX設計と対話デザイン
4.1 入出力インターフェース要件

| 項目 | 設計仕様 | 意図・体験上の理由 |
|------|----------|-------------------|
| **通知（トリガー）** | 画面端への控えめなアイコン表示＋微弱振動。「💡 気づきのヒントがあります」のみを通知する。 | 没入感を損なわず、ユーザーが自ら気づきを求める余白を維持するため。 |
| **視点表示（Primary Output）** | 576×288px領域に50文字以内・1〜2文のテキストを単色表示。3〜5秒で自動消灯（Auto-Dismiss）。 | 文字を読むことに意識を奪われず、視線を素早く現実世界へ戻せるようにするため。 |
| **深掘り（Action）** | G2のシングルタップで3つ以内の短い候補を開き、スライドで選択してタップで決定する。 | 低遅延・オフライン・予測可能な操作で、興味を持った場合のみ段階的に情報を取得できるため。 |

4.2 操作マッピングとインターフェース設計
（ハンズフリー・低侵襲UX）

誤操作を極力防ぎ、ユーザーの視野と意識を常に「世界」へ向けられるよう、以下のジェスチャー操作および自動消灯仕様を採用する。

| 操作（Action） | 機能（Function） | UX設計意図・メリット |
|----------------|------------------|----------------------|
| **パッシブ（自動検知）** | ささやきの受取・通知 | 移動・滞在などの文脈変化をAIが自動認識し、微弱振動とアイコンのみで通知する。手動生成を不要とし、誤操作を排除する。 |
| **シングルタップ** | 深掘り候補を開く／選択を決定 | 「この場所の背景」「別の見方」「自分への問い」から意図を選び、自由入力なしで段階的に深掘りする。 |
| **後方スライド**（または下スライド） | 別の視点（Next Whisper） | 情報を次へ送る感覚で、現在とは異なる角度からの視点や問いかけをリクエストする。 |
| **前方スライド**（または上スライド） | 飛ばす／閉じる（Dismiss）／クリア | 表示を視界の外へ押し上げる感覚で即座に消去し、意識を現実世界へ戻す。 |
| **放置（5秒タイムアウト）** | 自動消灯（Auto-Dismiss） | 候補選択中を除き、無操作状態が5秒続くと自動的にフェードアウトし、旅の余白を妨げない完全非侵襲UXを実現する。 |
| **候補表示中の後方／下スライド** | 次の深掘り候補 | 最大3件の短い候補内を順方向に循環する。 |
| **候補表示中の前方／上スライド** | 前の深掘り候補 | 最大3件の短い候補内を逆方向に循環する。 |
| **候補表示中のダブルタップ** | 選択を取り消して戻る | 候補を確定せず直前のささやきへ戻し、5秒の表示時間を取り直す。 |
| **長押し** | 終了確認／アプリ終了 | Even共通の終了確認を利用し、アプリ側では終了ジェスチャーを重複実装しない。 |
| **通常表示のダブルタップ** | 操作なし | 誤終了を防ぎ、将来の機能拡張余地を残す。 |
| **音声入力** | 将来の任意拡張 | 外部STTを中核依存にせず、SDK標準の低遅延音声認識と安全な終了操作が利用可能になった時点で再評価する。 |

4.2.1 開発段階の代替操作

本番UXの操作仕様は上記を正式基準とする。一方、Phase 2の開発・実機検証では、文脈監視やタイマー処理とG2表示／状態遷移の問題を切り分けるため、次の機能をスマホ画面の明示操作で代替できるようにする。

| 本番機能 | 開発段階の代替操作 | 検証目的 |
|----------|--------------------|----------|
| **パッシブ通知** | スマホ画面の「通知を発生」ボタン | 文脈の自動検知を待たず、通知アイコン・表示状態・後続ジェスチャーを再現可能にする。 |
| **5秒自動消灯** | スマホ画面の「表示を消す」ボタン | タイマーを待たず、Dismiss後の状態と再通知可否を決定的に確認する。 |

代替操作は開発・診断用に限定し、本番UXの操作マッピングを変更するものではない。自動検知と5秒タイマーは、G2側の表示・深掘り・閉じる・別視点の状態遷移が安定した後に接続する。

Phase 2 v0.7.0では5秒自動消灯を表示ライフサイクルへ接続する。Primary、深掘り、別視点の各表示でタイマーを開始または更新し、手動消去、新規通知、終了時に解除する。開発・実機検証ではスマホ画面から有効・無効を切り替えられるが、本番仕様は有効を基準とする。位置判定や通知条件とは独立した単一タイマーとして管理し、古いタイマーが新しい表示を消去しない構造とする。

Phase 2 v0.8.0では通知条件を決める前の実地観察として、ユーザーが実際の行動ラベルを明示してSDK診断値を記録できるようにする。観察ログはSDKアダプターおよび`ContextTimeline`から分離し、アプリセッションのメモリ内だけで管理する。出力には経過時間、受信・採用・除外件数、アプリの移動判定、距離、変位、計算速度、滞在時間、最新精度、アプリ状態を含めるが、緯度、経度、地名、生の位置履歴は含めない。ユーザーの`stationary`は一時的な停止、`dwelling`は観光・休憩など同じ場所への意図的な滞在を表し、アプリ計算結果の`movementState`とは分けて記録する。収集結果は行動認識精度の主張ではなく、通知適格性、クールダウン、重複抑制、滞在通知を決める材料として扱う。

Phase 2 v0.9.0では、外部音声認識を中核UXから外し、最大3件の選択式深掘りを正式な基本仕様とする。通常のささやきでシングルタップすると候補を開き、後方／下スライドで次、前方／上スライドで前の候補へ移動し、シングルタップで決定する。候補選択中は自動消灯を停止し、ダブルタップで選択を取り消して直前のささやきへ戻す。選択結果または戻したささやきには新しい5秒の自動消灯を適用する。アプリ終了はEven共通の長押し確認に委ね、通常表示のダブルタップには機能を割り当てない。候補と生成結果は入力方式に依存しない`DeepenIntent`で接続し、将来SDK標準音声認識が利用可能になった場合も同じ意図へ変換できる構造とする。

4.3 設計方針

本インターフェースは、「情報を見せる」のではなく、「気づきをそっと差し出す」ことを目的として設計する。

設計の基本原則は以下のとおりである。

- **最小限の通知**によって没入感を維持する
- **短時間表示・自動消灯**により視線を現実世界へ戻す
- **興味を持った場合のみ深掘りできる段階的な情報提示**を採用する
- **誤操作を防ぐシンプルなジェスチャー体系**を実現する
- **旅の主役は現実世界であり、AIはあくまで静かに寄り添う存在**として振る舞う

4.4 SDK-first実装原則

端末・OSと密接な機能は、Even Hub SDKに標準機能が存在する場合、自前実装よりSDKを優先する。位置情報については、アプリ独自の定期ポーリングではなく、SDKの連続位置更新、更新間隔、距離フィルター、開始・停止機能を使用する。

アプリ側の責務は、SDK差分を吸収する薄いアダプター、受信データの一時的な保持、World Whisper固有の文脈解釈に限定する。移動手段を断定することよりも、位置が安定しているか、意味のある文脈変化が起きたか、一定範囲に滞在しているかを判定する。

Google Maps Platformなどの外部サービスは、移動検出を置き換える目的では導入しない。将来、周辺施設、地名、歴史・文化的背景など場所の意味づけが必要になった段階で、APIキーをクライアントへ保存しないバックエンド経由の構成として検討する。

5. 段階的開発ロードマップ
フェーズ 1：PoC（プロトタイプ検証）
目標： 位置情報＋外部LLMによる「視点生成プロンプト」の品質検証。
実装内容： スマホアプリ単体（Web/React Native）で位置情報を拾い、ボタンプッシュまたは手動トリガーで1文の「ささやき」を画面表示・音声出力する仕組みの構築。
フェーズ 2：Even G2 実機連携とコンテキスト拡充
目標： Even Hub SDKを用いたスマートグラスへの描画および控えめな通知UXの実装。
実装内容： SDK連携、位置の安定・文脈変化・滞在時間の解釈、G2のディスプレイスペックに合わせた文字数制御・フォーマットの最適化。
フェーズ 3：パーソナライズと高精度ナレッジ連携
目標： ユーザーの過去の応答履歴（深掘りした/無視した）をフィードバックした対話モデルの学習・調整。
実装内容： 長期記憶データベースの構築、位置連動ナレッジグラフの自動参照機能の実装。

| コンポーネント | 技術スタック / デバイス | 役割と処理内容 |
| --- | --- | --- |
| UI/Display | Even G2 (Monochrome Micro-LED) | ささやき（視点）を提示する1〜2文の短いテキスト描画、気づき通知のポップアップ表示、マイクによる音声拾い上げ。 |
| Client Core | TypeScript / React / (@evenrealities/even_hub_sdk) | SDK位置情報と時刻の取得、位置履歴からの文脈変化・滞在の解釈、バックエンドとの通信、G2へのレンダリング指示。 |
| Context & Backend | Python (FastAPI) または Node.js | 位置情報から周辺の歴史・文化・地理情報を補完。直近の移動履歴と組み合わせてLLMへの入力プロンプトを構成。 |
| AI Engine | 外部LLM API (Gemini等) | 入力された文脈データから、「ユーザーの観察や内省を促す1つの問いかけ・視点」を生成。文字数やトーンの制御。 |
